\section{System Testing}

\subsection{Introduction}

Software Testing is one of the most critical phases in the software development lifecycle, aimed at verifying that the system functions correctly according to its specifications, meets quality standards, and minimizes defects before deployment. A well-structured testing process improves the reliability, maintainability, and overall stability of the software.

For the \textbf{LivingDocs AI-Assisted Documentation System}, testing is particularly important because the platform integrates multiple interconnected components, including GitHub Integration, a Spring Boot Backend, a Python FastAPI AI Service, Supabase PostgreSQL with pgvector, and a multi-level Review Workflow. Since these services communicate continuously, failures in synchronization or document generation could affect the entire documentation update process.

At the current development stage, the project focuses on establishing a comprehensive testing strategy while implementing functional testing for the integrated React Frontend and Spring Boot Backend. More advanced testing activities, such as fully automated CI/CD regression testing and production-level GitHub synchronization, will be completed in later iterations.

The objective of this testing plan is to provide a systematic quality assurance process that verifies core business logic and critical user workflows before the final system release.

\subsection{Testing Objectives}

The testing process is designed to achieve the following objectives:

\begin{itemize}
	\item Verify that implemented features behave according to the Software Requirements Specification.
	\item Detect software defects as early as possible.
	\item Validate communication between the React Frontend, Spring Boot Backend, FastAPI AI Service, and Supabase PostgreSQL.
	\item Verify AI-generated documentation suggestions displayed in the review interface.
	\item Ensure system stability during common user interactions.
	\item Support continuous quality improvement throughout development.
\end{itemize}

\subsection{Testing Scope}

The testing scope covers the major functional modules of the current LivingDocs implementation.

\paragraph{GitHub Integration}

Testing repository connection, webhook reception, and synchronization behaviour.

\paragraph{AI Documentation Generation}

Testing document suggestion generation and semantic matching using the FastAPI AI service.

\paragraph{Automatic Documentation Update}

Testing whether code changes correctly trigger documentation update suggestions.

\paragraph{Documentation Drift Detection}

Testing drift severity classification (Low, Medium, High, Critical).

\paragraph{Knowledge Base}

Testing document retrieval and version comparison.

\paragraph{Review Workflow}

Testing Staff review, approval actions, and Manager publication simulation.

\paragraph{Administration}

Testing role-based access behaviour and workspace management.

\subsection{Testing Strategy}

LivingDocs adopts a layered testing strategy combining several testing methodologies.

\paragraph{Black-box Testing}

Used for validating user-facing features implemented in ReactJS, including the Review Queue Dashboard and the Workspace Split View.

\paragraph{White-box Testing}

Applied to backend components implemented with Spring Boot and FastAPI to verify internal logic and API behaviour.

\paragraph{Integration Testing}

Verifies communication among ReactJS, Spring Boot, FastAPI, and Supabase services.

\paragraph{Regression Testing}

Planned for future CI/CD automation to ensure new changes do not break existing functionality.

\paragraph{User Acceptance Testing}

Realistic user scenarios are executed to validate business requirements.

\subsection{Testing Levels}

Testing activities are divided into four levels.

\paragraph{Unit Testing}

Testing individual functions and classes independently.

\paragraph{Integration Testing}

Testing interactions among Backend services and the database.

\paragraph{System Testing}

Testing the complete integrated LivingDocs application.

\paragraph{Acceptance Testing}

Validating whether the system satisfies user expectations.

\subsection{Defect Management}

Detected defects follow a structured workflow.

\begin{enumerate}
	\item Tester reports the issue.
	\item Bug is logged in Jira.
	\item Severity is assigned.
	\item Developer fixes the issue.
	\item Tester performs Retest and Regression Testing.
	\item Bug is closed after verification.
\end{enumerate}

Defects are categorized into Critical, High, Medium, and Low severity.

\subsection{Testing Monitoring}

The team tracks several testing indicators.

\begin{itemize}
	\item Executed test cases.
	\item Pass rate.
	\item Active defects.
	\item Resolution time.
\end{itemize}

A Test Summary Report will be generated at the end of each sprint.
