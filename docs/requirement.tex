\section{System Requirements}

\subsection{Requirements Introduction}

Tài liệu này mô tả các yêu cầu chức năng và phi chức năng của hệ thống \textbf{LivingDocs} trong phạm vi dự án Công nghệ Phần mềm. Mục tiêu của phần yêu cầu là xác định rõ những chức năng hệ thống cần cung cấp, các điều kiện hoạt động, cũng như các ràng buộc kỹ thuật cần tuân thủ trong quá trình thiết kế và triển khai.

Hệ thống LivingDocs được xây dựng nhằm hỗ trợ đồng bộ tài liệu kỹ thuật với mã nguồn được quản lý trên GitHub. Việc xác định đầy đủ yêu cầu giúp đảm bảo hệ thống đáp ứng đúng nhu cầu quản lý tài liệu, theo dõi thay đổi mã nguồn và hỗ trợ quy trình phát triển phần mềm hiện đại.

\paragraph{Phạm vi hệ thống}

Phạm vi của hệ thống bao gồm:

\begin{itemize}
    \item Kết nối tài khoản GitHub thông qua cơ chế OAuth2.
    \item Quản lý repository cần theo dõi và đồng bộ.
    \item Theo dõi commit, branch và Pull Request.
    \item Đồng bộ tự động dữ liệu mã nguồn với hệ thống LivingDocs.
    \item Hỗ trợ tích hợp CI/CD để tự động cập nhật tài liệu khi có thay đổi mã nguồn.
\end{itemize}

Những yêu cầu này đóng vai trò nền tảng cho việc thiết kế kiến trúc hệ thống và triển khai các thành phần GitHub Integration của LivingDocs.

\subsection{Functional Requirements}

\subsubsection{FR1: GitHub Authentication Using OAuth2}

Hệ thống phải cho phép người dùng đăng nhập và kết nối tài khoản GitHub bằng giao thức \textbf{OAuth2}.

\paragraph{Mô tả}

\begin{itemize}
    \item Người dùng chọn chức năng \textbf{Connect GitHub}.
    \item Hệ thống chuyển hướng đến trang xác thực GitHub.
    \item Sau khi người dùng cấp quyền truy cập, hệ thống nhận được \texttt{authorization code}.
    \item Mã xác thực được trao đổi để lấy \texttt{access token}.
    \item Token được lưu trữ an toàn để sử dụng cho các yêu cầu API tiếp theo.
\end{itemize}

\paragraph{Kết quả mong đợi}

Người dùng có thể kết nối thành công tài khoản GitHub mà không cần cung cấp mật khẩu trực tiếp cho LivingDocs.

\subsubsection{FR2: Repository Selection and Management}

Hệ thống phải cho phép người dùng lựa chọn repository cần quản lý sau khi xác thực GitHub thành công.

\paragraph{Mô tả}

\begin{itemize}
    \item Hiển thị danh sách repository mà người dùng có quyền truy cập.
    \item Cho phép chọn một hoặc nhiều repository.
    \item Lưu thông tin repository bao gồm tên, owner, branch mặc định và thời gian đồng bộ gần nhất.
\end{itemize}

\paragraph{Kết quả mong đợi}

Repository được thêm vào workspace của LivingDocs và sẵn sàng cho quá trình đồng bộ tự động.

\subsubsection{FR3: Commit and Pull Request Synchronization}

Hệ thống phải đồng bộ thông tin commit và Pull Request từ GitHub với LivingDocs.

\paragraph{Mô tả}

\begin{itemize}
    \item Lấy danh sách commit mới từ branch chính.
    \item Theo dõi Pull Request được tạo, cập nhật hoặc merge.
    \item Ghi nhận danh sách file thay đổi trong mỗi Pull Request.
    \item Liên kết thay đổi mã nguồn với tài liệu liên quan trong LivingDocs.
\end{itemize}

\paragraph{Kết quả mong đợi}

LivingDocs luôn phản ánh trạng thái mới nhất của mã nguồn trong repository GitHub.

\subsubsection{FR4: CI/CD Integration for Automatic Documentation Update}

Hệ thống phải hỗ trợ tích hợp với \textbf{GitHub Actions} hoặc công cụ CI/CD tương đương để tự động cập nhật tài liệu.

\paragraph{Mô tả}

\begin{itemize}
    \item Kích hoạt workflow khi có commit hoặc Pull Request mới.
    \item Build và kiểm tra mã nguồn tự động.
    \item Gửi thông tin thay đổi đến LivingDocs thông qua API nội bộ.
    \item Tự động tạo hoặc cập nhật tài liệu liên quan sau khi Pull Request được merge.
\end{itemize}

\paragraph{Kết quả mong đợi}

Tài liệu kỹ thuật được cập nhật tự động mà không cần thao tác thủ công từ người dùng.

\subsubsection{FR5: Synchronization Status Management}

Hệ thống phải quản lý và hiển thị trạng thái của quá trình đồng bộ.

\paragraph{Mô tả}

\begin{itemize}
    \item Theo dõi trạng thái \texttt{SUCCESS}, \texttt{FAILED} hoặc \texttt{PENDING}.
    \item Lưu thời gian bắt đầu và kết thúc đồng bộ.
    \item Ghi nhận thông tin lỗi nếu quá trình đồng bộ thất bại.
    \item Cho phép người dùng thực hiện đồng bộ lại khi cần thiết.
\end{itemize}

\paragraph{Kết quả mong đợi}

Người dùng có thể theo dõi và kiểm soát toàn bộ quá trình đồng bộ giữa GitHub và LivingDocs.

\subsubsection{FR6: Static Code Analysis and AI Documentation Generation}

Hệ thống phải tự động phân tích cấu trúc mã nguồn và sinh ra tài liệu kỹ thuật chi tiết bằng cách tích hợp các Mô hình Ngôn ngữ Lớn (LLM).

\paragraph{Mô tả}

\begin{itemize}
    \item Tự động trích xuất Cây Cú pháp Trừu tượng (\texttt{Abstract Syntax Tree - AST}) từ các tệp mã nguồn để xác định danh sách các hàm, lớp, tham số, kiểu dữ liệu trả về và các điểm cuối API (\texttt{API Endpoints}).
    \item Đóng gói thông tin cấu trúc mã nguồn cùng các đoạn ghi chú (\texttt{inline comments}) gửi đến AI Engine thông qua các mẫu prompt được chuẩn hóa.
    \item Sinh nội dung tài liệu kỹ thuật chi tiết bao gồm: Mô tả chức năng hàm/lớp, Tài liệu API Specifications (đầy đủ Request/Response/Status Code), và Tài liệu Hướng dẫn Sử dụng.
    \item Hỗ trợ xuất và định dạng kết quả theo chuẩn Markdown hoặc mã nguồn LaTeX sẵn sàng để xuất bản.
\end{itemize}

\paragraph{Kết quả mong đợi}

Tài liệu kỹ thuật được khởi tạo tự động có cấu trúc chặt chẽ, chính xác và phản ánh đúng 100\% khai báo mã nguồn mà không cần kỹ sư viết tay thủ công.

\subsubsection{FR7: Context Management and Retrieval-Augmented Generation (RAG)}

Hệ thống phải triển khai kiến trúc RAG để truy vấn ngữ cảnh dự án toàn cục, nâng cao độ chính xác khi sinh tài liệu.

\paragraph{Mô tả}

\begin{itemize}
    \item Tự động chia nhỏ (\texttt{code chunking}) và chuyển đổi tài liệu cùng mã nguồn dự án thành dạng nhúng vector (\texttt{vector embeddings}) thông qua Embedding Model.
    \item Lưu trữ và đánh chỉ mục dữ liệu vector trong Cơ sở dữ liệu Vector (\texttt{Vector Database}).
    \item Khi phát sinh yêu cầu sinh tài liệu, hệ thống thực hiện tìm kiếm ngữ nghĩa (\texttt{semantic search}) để trích xuất các đoạn văn bản/mã nguồn liên quan nhất trong toàn bộ dự án làm ngữ cảnh bổ sung cho AI.
    \item Kiểm soát và tối ưu hóa dung lượng ngữ cảnh (\texttt{context window}) để đảm bảo không vượt quá giới hạn token của LLM.
\end{itemize}

\paragraph{Kết quả mong đợi}

AI Engine nắm bắt được mối liên hệ toàn cục giữa các module, loại bỏ hoàn toàn hiện tượng "ảo giác" (\texttt{hallucination}) hoặc đưa ra thông tin không có trong codebase.

\subsubsection{FR8: Automated Architecture and Diagram Generation}

Hệ thống phải phân tích kiến trúc mã nguồn và tự động tạo mã nguồn biểu đồ kỹ thuật.

\paragraph{Mô tả}

\begin{itemize}
    \item Phân tích mối quan hệ phụ thuộc (\texttt{dependencies}), quan hệ kế thừa và giao tiếp giữa các lớp/module trong dự án.
    \item Tự động sinh mã biểu đồ theo cú pháp Mermaid.js hoặc PlantUML cho Sơ đồ Lớp (\texttt{Class Diagram}), Sơ đồ Tuần tự (\texttt{Sequence Diagram}) và Sơ đồ Luồng dữ liệu (\texttt{Data Flow Diagram}).
    \item Kiểm tra tính hợp lệ cú pháp của đoạn mã biểu đồ sinh ra trước khi trả về giao diện.
\end{itemize}

\paragraph{Kết quả mong đợi}

Các biểu đồ kiến trúc hệ thống được vẽ tự động, có khả năng render trực quan trên giao diện web và tự động vẽ lại khi kiến trúc mã nguồn thay đổi.

\subsubsection{FR9: Documentation Drift Detection and Alerting}

Hệ thống phải tự động phát hiện sự lệch ngữ cảnh (\texttt{Documentation Drift}) giữa tài liệu lưu trữ và mã nguồn thực tế.

\paragraph{Mô tả}

\begin{itemize}
    \item Khi có commit mới, hệ thống phân tích sự thay đổi mã nguồn (\texttt{Code Diff}) và so sánh với phiên bản tài liệu hiện tại trong cơ sở dữ liệu.
    \item Phát hiện các trường hợp mâu thuẫn như: hàm bị đổi tên/chữ ký, tham số API bị thêm/xóa, hoặc logic nghiệp vụ đã thay đổi nhưng tài liệu chưa cập nhật.
    \item Ghi nhận mức độ lệch ngữ cảnh và hiển thị cảnh báo trực quan kèm vị trí tài liệu bị lỗi thời cho người dùng.
\end{itemize}

\paragraph{Kết quả mong đợi}

Giúp nhóm phát triển ngay lập tức nhận biết các phần tài liệu cần được cập nhật, ngăn chặn tình trạng tài liệu bị lỗi thời so với thực tế.

\subsubsection{FR10: Human-in-the-Loop Review and Proposal Management}

Hệ thống phải cung cấp quy trình kiểm duyệt và chỉnh sửa trực quan dành cho người dùng trước khi áp dụng tài liệu mới do AI sinh ra.

\paragraph{Mô tả}

\begin{itemize}
    \item Tài liệu sau khi AI sinh ra được lưu dưới dạng Đề xuất cập nhật (\texttt{Documentation Proposal}) ở trạng thái bản thảo (\texttt{DRAFT\_REVIEW}).
    \item Cung cấp giao diện so sánh song song (Side-by-Side Diff) giữa mã nguồn vừa thay đổi và nội dung tài liệu đề xuất.
    \item Cho phép kỹ sư chỉnh sửa trực tiếp nội dung bản thảo, thêm bớt ghi chú trước khi bấm xác nhận (\textbf{Approve \& Merge}).
    \item Đồng bộ tài liệu đã duyệt vào branch chính và cập nhật lại chỉ mục Vector DB.
\end{itemize}

\paragraph{Kết quả mong đợi}

Đảm bảo tính kiểm soát tuyệt đối của con người đối với sản phẩm do AI tạo ra, kết hợp tốc độ của AI và độ tin cậy của chuyên gia phần mềm.

\subsection{Non-Functional Requirements}

\subsubsection{NFR1: Security}

Hệ thống phải đảm bảo an toàn cho dữ liệu và thông tin xác thực của người dùng.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Access token phải được mã hóa trước khi lưu trữ.
    \item Chỉ sử dụng kết nối HTTPS/TLS khi giao tiếp với GitHub API.
    \item Áp dụng cơ chế phân quyền truy cập theo vai trò người dùng.
    \item Không ghi dữ liệu nhạy cảm vào log hệ thống.
\end{itemize}

\subsubsection{NFR2: Performance}

Quá trình đồng bộ phải hoạt động hiệu quả và không ảnh hưởng đáng kể đến hệ thống chính.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Đồng bộ incremental thay vì tải lại toàn bộ repository.
    \item Ưu tiên xử lý bất đồng bộ đối với các tác vụ phân tích lớn.
    \item Thời gian phản hồi của API phải đủ nhanh để hỗ trợ trải nghiệm người dùng.
\end{itemize}

\subsubsection{NFR3: Scalability}

Hệ thống phải có khả năng mở rộng để phục vụ nhiều repository và nhiều người dùng đồng thời.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Hỗ trợ quản lý nhiều repository trong cùng một tài khoản.
    \item Cho phép nhiều người dùng sử dụng hệ thống đồng thời.
    \item Thiết kế dịch vụ theo hướng module hóa để dễ dàng mở rộng trong tương lai.
\end{itemize}

\subsubsection{NFR4: Reliability and Recovery}

Hệ thống phải duy trì tính ổn định và có khả năng phục hồi khi xảy ra lỗi kết nối hoặc lỗi dịch vụ bên ngoài.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Tự động thử lại khi GitHub API tạm thời không phản hồi.
    \item Lưu trạng thái đồng bộ để tiếp tục xử lý sau khi phục hồi.
    \item Ghi log chi tiết để hỗ trợ giám sát và khắc phục sự cố.
\end{itemize}

\subsubsection{NFR5: Usability}

Giao diện người dùng phải trực quan và dễ sử dụng đối với thành viên nhóm phát triển phần mềm.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Các chức năng kết nối GitHub và đồng bộ phải dễ tìm thấy.
    \item Hiển thị trạng thái đồng bộ rõ ràng bằng biểu tượng hoặc màu sắc.
    \item Cung cấp thông báo lỗi và hướng dẫn xử lý khi xảy ra sự cố.
\end{itemize}

\subsubsection{NFR6: AI Output Accuracy and Quality Control}

Nội dung tài liệu do AI Engine sinh ra phải đạt các tiêu chuẩn khắt khe về độ chính xác kỹ thuật và định dạng.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Tỷ lệ cú pháp Markdown, mã LaTeX và sơ đồ Mermaid sinh ra phải đạt độ hợp lệ tối thiểu $98\%$ (không bị lỗi render giao diện).
    \item Tỷ lệ thông tin sai lệch hoặc bịa đặt (Hallucination Rate) phải được kiểm soát dưới $2\%$ nhờ cơ chế RAG và bộ kiểm tra AST.
    \item Tất cả các tên hàm, biến, lớp và đường dẫn API trong tài liệu phải khớp $100\%$ với mã nguồn thực tế.
\end{itemize}

\subsubsection{NFR7: AI Security, Privacy and Zero Data Retention}

Hệ thống phải bảo đảm an toàn tuyệt đối cho quyền sở hữu trí tuệ, mã nguồn doanh nghiệp và dữ liệu cá nhân.

\paragraph{Yêu cầu}

\begin{itemize}
    \item \textbf{Zero Data Retention}: Bắt buộc sử dụng các cổng API doanh nghiệp (Enterprise API) có cam kết không lưu trữ hoặc sử dụng mã nguồn của dự án để huấn luyện lại mô hình AI.
    \item \textbf{Data Masking}: Tự động quét và loại bỏ/mã hóa các thông tin nhạy cảm như API Keys, Passwords, Token xác thực và Thông tin Định danh Cá nhân (\texttt{PII}) trước khi truyền payload sang AI Service.
    \item Toàn bộ dữ liệu truyền nhận với dịch vụ AI phải được mã hóa chuẩn HTTPS/TLS 1.3.
\end{itemize}

\subsubsection{NFR8: Fault Tolerance and AI Model Fallback}

Hệ thống phải duy trì khả năng hoạt động liên tục và chịu lỗi tốt khi các dịch vụ AI bên ngoài gặp sự cố.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Áp dụng thuật toán \textbf{Exponential Backoff Retry} khi gặp lỗi nghẽn mạng hoặc chạm giới hạn request (\texttt{rate limit}) của AI API.
    \item Thiết lập cơ chế chuyển đổi mô hình tự động (\textbf{Model Fallback}): Nếu mô hình AI chính (như GPT-4) không phản hồi, hệ thống tự động chuyển sang mô hình dự phòng (như Claude hoặc Gemini).
    \item Trường hợp toàn bộ dịch vụ AI bị gián đoạn, hệ thống phải kích hoạt chế độ sinh tài liệu cơ bản dựa trên khung mẫu (\texttt{Template-based}) trích xuất từ AST mà không làm ngắt quãng quy trình hệ thống.
\end{itemize}

\subsubsection{NFR9: AI Latency and Cost Optimization}

Quá trình sinh tài liệu bằng AI phải tối ưu thời gian phản hồi và kiểm soát chi phí sử dụng API.

\paragraph{Yêu cầu}

\begin{itemize}
    \item Thời gian sinh tài liệu hoàn chỉnh (End-to-End Latency) không vượt quá $10$ giây đối với các commit có quy mô trung bình.
    \item Chỉ gửi phần mã nguồn thay đổi (\texttt{Code Diff}) thay vì toàn bộ tệp nguồn để tiết kiệm ít nhất $60\%$ lượng token tiêu thụ.
    \item Áp dụng cơ chế Caching đối với các truy vấn RAG và prompt trùng lặp để giảm thiểu số lần gọi API không cần thiết.
\end{itemize}

\subsection{System Constraints}

\subsubsection{Official GitHub API}

Hệ thống phải sử dụng \textbf{GitHub REST API} hoặc \textbf{GitHub GraphQL API} chính thức để đảm bảo tính tương thích và tuân thủ chính sách của GitHub.

\subsubsection{Repository Access Scope}

Hệ thống chỉ hỗ trợ các repository:

\begin{itemize}
    \item Public repository.
    \item Private repository mà người dùng đã cấp quyền truy cập thông qua OAuth2.
\end{itemize}

Những repository không có quyền truy cập hợp lệ sẽ không được phép đồng bộ với LivingDocs.

\subsubsection{LivingDocs Internal API Integration}

Việc trao đổi dữ liệu giữa GitHub Integration và LivingDocs phải được thực hiện thông qua \textbf{API nội bộ} của hệ thống.

\paragraph{Ràng buộc}

\begin{itemize}
    \item Chỉ các dịch vụ được xác thực mới được phép gọi API nội bộ.
    \item Dữ liệu đồng bộ phải tuân theo định dạng chuẩn do LivingDocs quy định.
    \item Mọi yêu cầu cập nhật tài liệu phải được kiểm tra quyền truy cập trước khi xử lý.
\end{itemize}

\subsection{Conclusion}

Phần yêu cầu hệ thống đã xác định các yêu cầu chức năng và phi chức năng quan trọng của hệ thống \textbf{LivingDocs}. Các yêu cầu chức năng tập trung vào việc kết nối GitHub bằng OAuth2, quản lý repository, đồng bộ commit và Pull Request, tích hợp CI/CD và quản lý trạng thái đồng bộ. Đồng thời, các yêu cầu phi chức năng đảm bảo hệ thống đáp ứng các tiêu chí về bảo mật, hiệu năng, khả năng mở rộng, độ ổn định và tính dễ sử dụng.

Việc tích hợp GitHub đóng vai trò cốt lõi trong kiến trúc LivingDocs vì nó giúp hệ thống theo dõi chính xác mọi thay đổi của mã nguồn và tự động cập nhật tài liệu tương ứng. Điều này góp phần đảm bảo tài liệu kỹ thuật luôn \textbf{cập nhật, nhất quán và phản ánh đúng trạng thái thực tế của hệ thống phần mềm}, từ đó nâng cao chất lượng quản lý dự án và hiệu quả phối hợp của nhóm phát triển.
